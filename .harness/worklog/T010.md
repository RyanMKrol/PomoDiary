# T010: Rate limiting implementation

**Date:** 2026-08-11

## What was done

Implemented request rate limiting for the external API with Upstash Redis backend, built to fail gracefully (fail-open) when Redis is unavailable:

1. **Added dependencies**: `@upstash/redis@^1.35.0` and `@upstash/ratelimit@^2.0.8` to package.json

2. **Created `lib/ratelimit/index.ts`** with:
   - Lazy singleton clients for read and write rate limiting
   - `checkRateLimit(key: string, kind: "read" | "write")` function that returns `{ ok: boolean; retryAfterSeconds?: number }`
   - Sliding window rate limits: 120/min for reads, 60/min for writes
   - Separate Redis prefixes for read and write limits to keep them independent
   - Environment variables: `KV_REST_API_URL` and `KV_REST_API_TOKEN` (Vercel marketplace integration names)
   - Fail-open behavior: returns `{ ok: true }` with console.warn when env vars are missing or Redis errors occur
   - One-time warning per process to avoid log spam

3. **Key helper functions**:
   - `userKey(userId: string)` → `"user:<userId>"`
   - `ipKey(ip: string)` → `"ip:<ip>"`
   - `resetState()` (for testing) → clears module state

4. **Comprehensive unit tests** in `lib/ratelimit/index.test.ts`:
   - ✓ Allows requests under read limit (120/min)
   - ✓ Allows requests under write limit (60/min)
   - ✓ Blocks requests exceeding read limit with correct retryAfterSeconds
   - ✓ Blocks requests exceeding write limit with correct retryAfterSeconds
   - ✓ Fails open when `KV_REST_API_URL` is missing
   - ✓ Fails open when `KV_REST_API_TOKEN` is missing
   - ✓ Fails open on Redis errors with logged warning
   - All mocks use Upstash classes (no real Redis calls)

## Implementation notes

Used separate Ratelimit instances for read/write to maintain independent rate limit counters. The Upstash API requires each rate limit algorithm to be attached to a client at construction time, so two clients with different limiters provide the cleanest separation.

The fail-open design ensures:
- Local development and CI never require Redis credentials
- Production gracefully degrades if Redis is temporarily unavailable
- Operations team can deploy with confidence (availability > strictness)
