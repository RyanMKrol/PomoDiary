## Overview

The data-access layer over the T006 schema: everything the API needs to read and write entries
and timer state, with per-user storage caps enforced at this layer, tested hermetically on
PGlite.

## Do

In `lib/db/` add store modules (each function takes the Drizzle instance as its first argument
so tests inject the PGlite db):

1. `entries.store.ts`:
   - `insertEntry(db, userId, entry)` and `insertEntries(db, userId, entries[])` (away backfill).
   - `listEntriesForDay(db, userId, dayStartTs, dayEndTs)` — newest-first by `from`.
   - `listEntriesForRange(db, userId, fromTs, toTs)` — for the 10-day grid, newest-first.
   - `updateEntry(db, userId, entryId, patch)` — only `tag`, `feel`, `intent`, `bullets`
     patchable; must scope by BOTH entryId and userId (a user can never touch another user's row).
   - `countEntriesForDay(db, userId, dayStartTs, dayEndTs)`.
   - Hard caps enforced here (throw a typed `CapError`): max 100 entries per user per calendar
     day, max 30 bullets per entry, max 500 chars per bullet. The per-day cap is an ABUSE
     guard, not UX — compute its day window in UTC server-side (user timezones are irrelevant
     to it; UX day bucketing happens client-side, see T013).
2. `timer-state.store.ts`: `getTimerState(db, userId)` (null when absent),
   `upsertTimerState(db, userId, state)`, `getSettings(db, userId)` returning defaults
   (60/true/0.8/false) when absent, `upsertSettings(db, userId, patch)`.
3. Tests on the PGlite harness: cross-user isolation (user A cannot read/update user B's entry),
   each cap fires at its boundary (100th entry ok, 101st throws; 30 bullets ok, 31 throws;
   500-char bullet ok, 501 throws), day/range queries bucket correctly across midnight, updates
   patch only allowed fields.

## Done when

`npm test` passes; every listed function exists and is covered, including the three cap
boundaries and cross-user isolation, all against PGlite only.
